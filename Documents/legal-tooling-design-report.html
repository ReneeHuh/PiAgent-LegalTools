Pro Se Legal Tooling — Design Report

Assessment of three proposed tools and recommendations for the broader toolkit

Prepared 2026-08-29  ·  Workspace: CaseLawSearch  ·  Builds on the 2026-08-28 full review of pi-unified-legal-research v0.16.0

Executive summary

Three tools were proposed: (1) a case-law search tool, (2) a multi-try summarization agent with a consolidation step, and (3) a shepardizing tool that downloads a case plus its citing cases and produces an analysis report. The first already exists as the pi extension in this workspace. The second is a good instinct but should be reshaped from "3 tries + merge" into a draft → audit-against-source → correct pipeline, most of which is already written as prompts in this folder. The third is worthwhile but depends on legal_cited_by, which has two confirmed bugs that must be fixed first, and its output must be honestly labeled as citation analysis rather than true Shepard's validation.

Beyond the three proposals, the highest-value additions for pro se litigation are a quote-and-cite verifier for your own briefs (reuses the existing audit prompt almost verbatim), a deadline calculator (pure code, no LLM, maximally trustworthy), and an opposing-brief analyzer (composes tools you already have).

Recommended build order

1. Fix the two legal_cited_by bugs  →  2. Brief quote-and-cite verifier  →  3. Draft→audit→correct summarizer  →  4. Shepardizing report tool  →  5. Deadline calculator and remaining utilities.

Tool 1 — Case search Already built

The workspace already ships pi-unified-legal-research (v0.16.0) with five tools — legal_jurisdictions, legal_search, legal_cited_by, direct_download, legal_open_browser — backed by CourtListener and Google Scholar scraper engines, plus a bundled skill. All 69 unit tests pass and the skill's parameter schema exactly matches the code. This tool is done; the work remaining is maintenance, not design.

Known issues that affect the other tools

  • Cited-by ordering bug: a Google Scholar CAPTCHA pauses the entire run before CourtListener ever starts, and resume re-blocks on Scholar first. There is no way to run CourtListener alone.
  • Cited-by status bug: single-provider seeds (the normal case) mark the other provider "failed" at creation, so status can never reach "complete" and the resume advice loops forever.
  • Seed gate not enforced: .download-error-* sidecar files can seed cited-by runs despite the documented "only successfully saved cases" rule.
  • Coverage gap: no federal district courts in the jurisdiction vocabulary (circuits, SCOTUS, and state appellate only).
Dependency warning

The proposed shepardizing tool sits directly on top of legal_cited_by. Building it before fixing the two cited-by bugs means the shepardizer inherits unreliable, permanently-"incomplete" input. Fix the foundation first.

Tool 2 — Multi-try summarization agent Reshape the design

The proposal: run a task (e.g., summarize an opinion) three times, then consolidate the tries into a final answer. Running the same prompt N times and voting works well for discrete facts — disposition, dates, which party prevailed — where a majority vote catches a stray hallucination. It works poorly for prose: three stylistically different summaries are hard to merge, the merge step can introduce its own errors, and agreement between tries does not mean correctness, because models tend to fail the same way twice.

A stronger pattern is already half-built in this folder. summary prompt.txt defines a strict, structured summary format, and summary audit prompt.txt defines a proposition-by-proposition audit of a draft against the saved opinion text with a five-way support classification and a correction table. Auditing against the source catches hallucinations more reliably than comparing drafts to each other.

Recommended pipeline

1
Draft ×2 (parallel)Two independent summaries of the saved opinion using summary prompt.txt.
2
Audit against sourceOne auditor checks both drafts against the opinion text using summary audit prompt.txt, preferring the draft with fewer classification-(5) unsupported propositions.
3
Corrected outputFinal summary in the exact summary prompt.txt format, with the audit's correction table attached as an appendix so every fix is visible and verifiable.

This is cheaper than three tries plus consolidation, and the audit step — the part grounded in the actual opinion text — is where the real error-catching happens.

Tool 3 — Shepardizing / citation analysis Worthwhile, scope it honestly

The proposal: download a case, download all its citing cases, analyze, and produce a report. The download half already exists (legal_cited_by + direct_download). The genuinely valuable part to build is treatment classification: for each citing case, extract the passage that actually discusses the target case, classify the treatment, and aggregate the results into a signal report.

Design decisions

  • Treatment categories: followed · distinguished · criticized · limited · overruled · cited-in-passing. Aggregate into an overall signal (good law / caution / negative treatment found).
  • One hop only. Citing-cases-of-citing-cases explodes combinatorially. Cap the run at the target's direct citing cases, optionally trimmed to the top N by court level and recency.
  • Quote the evidence. The classifier must reproduce, word-for-word with pinpoints, the passage where each citing court discusses the target case — the same discipline the audit prompt already enforces. A treatment label without its supporting quotation is unverifiable and should not appear in the report.
  • Report structure: target case header → overall signal → negative treatment first (each with quoted passage and court level) → neutral/positive treatment → cases that could not be retrieved or classified, listed explicitly rather than silently dropped.
Honesty requirement

This is citation analysis, not Shepard's or KeyCite. CourtListener's citator has real coverage gaps, Google Scholar is CAPTCHA-flaky, and LLM treatment classification makes errors. The single worst failure mode is silently missing the one case that overruled your authority. The report must carry its own disclaimer: "Verify negative treatment on a commercial citator before relying on any authority in a filing." A tool that looks authoritative but has gaps is worse than no tool.

Recommended additional tools for pro se work

Ranked by how much each one actually protects you in front of a judge.

#ToolWhat it does and why it ranks here
1 Brief quote-and-cite verifier The audit prompt pointed at your own filings: verify every quotation in a draft brief word-for-word against the saved opinion, flag paraphrases presented as quotes, and check that each citation actually supports the proposition beside it. Misquoted authority is one of the fastest ways a pro se filer loses credibility with a court. Roughly 80% of the prompt is already written — build this before the shepardizer.
2 Deadline calculator Court-rule deadline computation with counting rules, weekend/holiday adjustments, and service-method extensions. (The summary prompt's "application for leave" / "in lieu of granting leave" language suggests Michigan appellate practice — MCR deadlines are mechanical and unforgiving.) Pure code, no LLM anywhere, which makes it the most trustworthy item on this list.
3 Opposing-brief analyzer Extract every citation from the other side's brief, run each through the summarizer, and flag where their characterization diverges from what the case actually says. Composes tools 2 and 3 above; this is where the case-law stack pays off most in a live dispute.
4 Table of authorities & formatting checker Generates the TOA and checks page limits, caption, and proof of service against local rules. Tedious, mechanical, and courts bounce filings over exactly this.
5 Statute & court-rule lookup The current stack is case-law only, but half of what a real brief cites is statutes and rules. Even a simple fetch-and-cache tool for statute/MCR text rounds out the corpus.

Architecture: one shared corpus

Every tool above — summarizer, shepardizer, brief verifier, opposing-brief analyzer — should read and write the same saved-case markdown store the extension already produces, keyed by the existing canonicalKey. One canonical record per case means a case downloaded during a shepardize run is immediately available to the summarizer and the brief verifier without re-fetching, and every quotation check in every tool resolves against the same source text. The extension is already most of the way there; the rule is simply that no new tool invents its own storage.

Caveats

  • These tools can make research faster and catch drafting errors, but nothing in this stack should be the last check before filing. Citator coverage gaps and LLM classification errors are real, and each tool's output should say so explicitly.
  • LLM output that asserts a quotation, holding, or treatment must always carry a verifiable pinpoint back to source text. The prompts in this folder already enforce that discipline — every new tool should inherit it.
  • None of this is legal advice, and a tool report is not a substitute for reading the controlling opinion.
