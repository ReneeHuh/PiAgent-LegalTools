Architecture and delivery plan · 26 August 2026

One Pi extension for a two-stage case-research workflow

Consolidate CourtListener, Google Scholar, FindLaw, and Justia behind one installed extension, one normalized case model, four explicit operating modes, and a clear boundary between finding candidate cases and checking selected authorities.

Recommended decision

Build a single extension package named legal-research, with one entry point and four source-neutral tools: legal_research for the four workflows, legal_read_case for chunked opinion reading, legal_record_case_check for recording proposition-specific opinion/citator review, and legal_open_browser for handing a provider tab to the user. Present those capabilities as two research stages: Stage 1 finds cases through ordinary search and exhaustive cited-by enumeration; Stage 2 downloads selected cases for full-opinion review, source-grounded briefing, and external citator checking. Provider adapters remain internal to the one installed extension.

Single installed unitOne extension appears in Pi. Multiple focused tools do not require multiple extensions.
Stage 1 — find and expandScholar-preferred ordinary search plus a complete-within-source cited-by report containing case identity, court/date, provider blurb, provenance, and links—never full opinions.
Stage 2 — check selected casesDownload and read only promoted cases, verify holdings and quotations, inspect relevant citing passages, and record Shepard's/KeyCite/BCite or other authorized validation outside the free citation graph.

Key outcome: users first build a complete lightweight candidate list, then spend download, model, and lawyer-review effort only on cases selected for detailed checking.

Optional enrichment: downloading workflows gain a summarize toggle, off by default. When enabled, the same extension creates one case.md companion with a source-grounded AI case brief and the extracted opinion text. No additional extension or public tool is required.

Current baseline and consolidation work

The repository currently contains two working standalone extensions: legal-research/provider-courtlistener.ts and legal-research/provider-google-scholar.ts. Both load successfully under Pi 0.84.3 and already implement the hard operational pieces: profile-specific Chrome discovery, raw CDP transport, visible verification handling, abort-aware waits, serialized navigation, tab leases, atomic manifests, paging, chunked reading, and HTML archiving.

The installed Pi 0.84.3 API also supports the proposed nested model call: a tool's ExtensionContext exposes ctx.model and ctx.modelRegistry, and ctx.modelRegistry.complete(...) can run an isolated completion. Pi tool results can return nested-model usage for session accounting. The local examples/extensions/summarize.ts demonstrates this exact model-registry path.

The consolidation should preserve those strengths while removing these seams:

  • Chrome/CDP, tab, timing, parsing, recovery, and saving logic is duplicated across the two files.
  • Public parameters differ: cluster_id versus case_id, and start versus start_page.
  • Save-path behavior is inconsistent: CourtListener resolves relative paths through Pi's context, while Scholar's direct reader currently passes save_dir through directly.
  • Search, download, read, and open-browser actions are split into provider-specific tool names rather than a source-neutral workflow.
  • There is no fixture-driven parser or provider contract test suite, making page-layout changes expensive to diagnose.

Packaging interpretation: “one extension” should mean one installed package and one entry point. Internally, keep small provider modules for maintainability, then bundle them into one distributable artifact. A single 3,000+ line source file would make future layout repairs riskier without improving the user experience.

Filter capability contract

Filters are capabilities, not hints. Every discovery adapter declares each filter as native, post_filter, or unsupported. The workflow preflights the complete request before opening a browser: an explicit or combined discovery source with an unsupported filter fails with a structured capability error; discovery auto chooses a provider that can honor the filter; and fallback skips incapable providers with an explanation.

Two research stages, implemented by four public modes

Stage 1 — find and expand search discovers ordinary candidates and cited_by exhaustively enumerates the selected providers' citation results into a lightweight report. search_download remains an explicit convenience when the user already wants every ordinary search result promoted for capture.
Stage 2 — check selected authorities A cited-by entry is promoted by passing its portable identity or provider URL to direct_download, then using legal_read_case, the optional evidence-linked case.md, and an external Shepard's/KeyCite/BCite review. Citation discovery never marks a case valid.

Stage boundary: cited-by collection records that one case cites another. It does not determine whether the citing court followed, distinguished, criticized, limited, or overruled the seed. Treatment belongs to Stage 2 and requires reading plus an authorized citator workflow.

1

search

Search Google Scholar by default, CourtListener as fallback, or both concurrently. Parse result-page titles, citations, courts, dates, snippets, provider IDs, and URLs; never open an opinion link.

May click their rendered Next controls until max_pages, max_results, end-of-results, or a hard provider ceiling. FindLaw and Justia are never queried in this mode.

2

search_download

Discover cases page-by-page through CourtListener/Scholar, then save each full opinion from the selected document source, return to discovery results, and click Next.

Stops at max_cases/max_pages, persists after every case, and resumes from a manifest rather than a global page coordinate. summarize=true queues a companion case.md.

3

cited_by

Resolve one seed independently in each selected citation provider, enumerate every reachable provider page or cursor, deduplicate parallel citations, and incrementally write a cited-by report.

The report contains only case name, citations, court/date, the preferred provider blurb, provider links, and provenance. This mode never opens opinions, downloads cases, or invokes the LLM. Long runs pause safely at time-slice boundaries and resume until exhausted.

4

direct_download

Resolve one specific case through CourtListener/Scholar (or accept a validated direct opinion URL), select a unique high-confidence document match, download that case only, and stop.

If the top candidates are ambiguous, return them without downloading rather than silently choosing the wrong case. A successful download may optionally produce case.md.

Reading is preserved: legal_read_case accepts a normalized case selector plus offset, returns 12,000-character opinion chunks to the conversation, and may optionally archive the unmodified HTML snapshot. Reading is a separate tool because it has a different output and continuation contract from the four workflows.

Stage 2 checking sequence

Promote selected candidate→Download exact opinion→Read full text→Identify proposition and exact passages→Review direct history and Shepard's/KeyCite/BCite→Record accepted, qualified, or rejected

The extension prepares and records this work but does not scrape a licensed citator without authorized access. Free Scholar/CourtListener citation results, provider blurbs, automated treatment-language detection, and an LLM case brief remain research leads—not a “good law” determination.

Mode state flows

Search:

Prefer Scholar or launch both lanes→Await page wave→Deduplicate→Scholar-first merge→Checkpoint and advance

Search and download:

Discover case→Resolve chosen document source→Validate opinion identity→Save→Restore discovery page→Next result/page

Cited by:

Resolve every seed identity→Enumerate all provider cursors/partitions→Checkpoint each page→Cross-source dedupe→Write metadata-only report→Exhaust or pause for resume

Direct download:

Resolve identity in CourtListener/Scholar→Lookup preferred document copy→Require unique match→Save one case→Stop

Proposed Pi tool contract

Register four tools from the one extension. Keep the four workflows in legal_research, keep chunk continuation in legal_read_case, record a user's completed opinion/citator review through legal_record_case_check, and keep visible browser handoff in legal_open_browser. The implementation uses one flat, enum-driven schema for legal_research and performs strict mode-specific validation before provider work. This avoids relying on TypeBox anyOf rendering while keeping all four workflows in one tool and one extension.

The TypeScript below is the conceptual discriminated contract. Its runtime JSON schema is flattened for harness compatibility; invalid cross-mode and selector-field combinations fail preflight.

Parameter rules

  • An omitted discovery_source means { strategy:"auto" }: Google Scholar first, with CourtListener as the capability/availability fallback. It never selects FindLaw or Justia. A filter Scholar cannot honor natively falls back to CourtListener before navigation.
  • Discovery fallback and combine accept only Scholar and CourtListener. combine launches one page request per provider concurrently in separate profile/tab lanes, then deduplicates and merges the completed page wave. Scholar is the default preferred tie-breaker unless preferred says otherwise; original provider ranks remain in provenance.
  • DocumentSelection.strategy:"discovery" downloads from the provider that found the case. fallback tries exact opinion copies in order and stops at the first high-confidence match; all_available may archive each validated copy while still counting one canonical case.
  • Every explicit provider list is non-empty and duplicate-free. Discovery lists are limited to CourtListener/Scholar; document lists may name any of the four providers.
  • A combined selection's preferred provider must appear in its provider list. When omitted and Scholar is present, Scholar is preferred; otherwise the first listed provider is preferred.
  • FindLaw and Justia receive only direct URLs/provider IDs or portable exact identity evidence such as a reporter citation or docket plus court. They never receive the user's broad query, discovery filters, result-page cursor, or cited-by request.
  • Any document provider other than the discovering/direct provider consumes one max_mirror_lookups unit. An alternative-document strategy with a zero budget fails preflight, and each exact resolver may inspect at most max_lookup_pages.
  • Page limits and request pacing apply independently per discovery lane; global result/case/runtime limits cap the workflow. The engine waits for both in-flight pages—or a recorded provider failure—before a deterministic merge, so network speed cannot change result order. It then starts the next concurrent page wave.
  • search accepts only discovery_source, has no document/download fields, and never visits an opinion page.
  • summarize is accepted only by workflows that save opinions: search_download and direct_download. It is off by default. The metadata-only cited_by mode rejects every download, document-source, mirror-lookup, and model field.
  • summary_model is valid only when summarize=true. It resolves a configured, session-allowed provider/model; when omitted, the extension uses ctx.model. Model availability and authentication are checked before browser work begins.
  • A CaseSelector is conceptually discriminated. The flat runtime schema rejects incompatible identity fields, so exactly one seed form is accepted and every provider ID names its provider.
  • direct_download saves exactly one canonical case only after the exact-match gate passes. A direct provider URL/ID bypasses discovery; explicit alternative document sources remain bounded exact lookups.
  • legal_record_case_check never infers or performs a commercial citator check. It records an explicit reviewer-supplied result against one proposition, validates any quoted passages against the downloaded opinion when available, and preserves the provider, timestamp, notes, and decision. Omitting citator leaves the case visibly not citator-checked.
  • discovery_sources is a non-empty, duplicate-free list and defaults to both citation providers. cited_by advances the selected graphs concurrently with independent pacing, cursors, partition queues, and failure state. Scholar supplies the preferred merged blurb when available; CourtListener remains the cursor-paginated enumeration backbone.
  • cited_by has no citer, page, or result cap. Its only execution bound is time_slice_minutes, which checkpoints and returns paused rather than declaring completion. Repeated resume calls continue from the first uncompleted provider cursor or partition until every selected graph is exhausted or blocked.
  • The cited-by report writes one entry per canonical citing case: case name, every known citation, court, filed date, provider blurb, blurb source, source URLs/IDs, discovery ranks, and the citation edge to the seed. A missing blurb is recorded as No result-page snippet provided; the extension never invents one.
  • Completing cited_by opens no citing opinion, downloads no full case, creates no case.md, and makes no nested model call. A user promotes a report entry into Stage 2 with a separate direct_download request.
  • start_page is one-based and valid only for one explicit CourtListener or Scholar discovery provider. Multi-provider and all resumable download workflows use resume_from.
  • Search and download workflows stop at their declared case/page/runtime bounds. Cited-by is the deliberate exception: it is exhaustive and resumable, with time slices controlling one invocation but never truncating the logical job.
  • A summary run uses at most six model calls per case by default and never more than twelve. If summarize=true, the bulk hard limit is 100 cases and preflight reports the maximum possible nested calls before navigation.
  • The workflow runtime budget includes browser and nested-model time. If it expires after downloads finish, unstarted summary jobs remain pending in the manifest rather than being mislabeled failed.
  • When a cited-by provider exposes a reliable total, progress reports projected pages before enumeration. Otherwise the total remains unknown and progress reports completed pages/cursors without fabricating a denominator.
  • Ordinary paged responses return completion: "exhausted" | "capped" | "partial_failure" | "cancelled". Cited-by returns "exhausted" | "paused" | "blocked" | "partial_failure" | "cancelled" per provider and for the merged job. Only exhausted means every result exposed by every selected provider was traversed. Even then, the public report says provider_corpus_complete: true and universe_complete: "not_claimed".

Compatibility decision

Ship deprecated wrappers for the eight existing CourtListener/Scholar tool names for one release cycle. Each wrapper validates the legacy parameters, translates them into the new engine, and emits a deprecation notice. Remove the aliases only in the next documented breaking release. This preserves existing prompts and sessions while making the migration decision now rather than after the port.

Discovery adapters own result/citation cursors and serialize them into the manifest; the workflow never assumes that both sources can be represented by one page number. A citation page carries its next cursor, observed total when available, provider access ceiling, partition identity, terminal evidence, and normalized lightweight cases, allowing the engine to checkpoint before any next-page navigation. Parsing a citation page must never invoke openOpinion.

Combined discovery uses a two-lane page barrier: Scholar and CourtListener navigate concurrently, each under its own profile, rate limiter, timeout, and abort signal. The merge starts only when the current wave settles. Scholar's rank is considered first, then CourtListener's, alternating thereafter; the next wave is not launched until the current merged results and both next cursors are checkpointed.

OpinionDocument must expose normalized text as deterministic, ordered source segments in addition to metadata and raw HTML. Segment IDs are derived from the source-text hash and ordinal, so summary evidence links remain stable across retries and cannot accidentally point into another case.

Pi-native model-call boundary

The summary worker calls ctx.modelRegistry.complete directly with a fresh, case-only message context. It does not inject a prompt into the main conversation, start another agent turn, or expose legal research tools to the nested completion. Use the active model by default, honor session model scoping, require configured authentication, pass cancellation through, set cache retention to none, and assign a fresh nested session ID. Aggregate every nested response's usage and return it on the parent tool result so Pi's session totals remain accurate.

Source-specific implementation notes

  • CourtListener: port the existing selectors and cites:(id) flow; retain canonical cluster URLs learned during search. For complete-within-source cited-by enumeration, prefer the current cursor-paginated citation API or authorized bulk citation data over fragile result-page traversal, and run until the terminal cursor.
  • Scholar: port the existing rendered form, case link, Back, Next, CAPTCHA, and 1,000-result-per-query ceiling logic. Where current access rules permit, partition a cited-by set deterministically by supported court/year constraints until every reachable shard is below the ceiling; persist the partition tree. A blocked, unpartitionable, or unexhausted shard makes Scholar incomplete—never bypass verification or access controls.
  • FindLaw: do not implement general Cludo paging. Accept allowlisted direct opinion URLs, or submit one exact citation/title lookup and inspect no more than max_lookup_pages for a confidence-gated match. Extract opinion text from #caselaw-content.
  • Justia: do not expose Google Custom Search as general discovery. Accept allowlisted direct opinion URLs, or use its search only for a bounded exact-case resolution. Support both state/federal pages with #opinion and Supreme Court pages with #opinions/#tab-opinion-*.

Preserve the existing CourtListener and Scholar Chrome profile directories during migration so cookies and verification state are not silently discarded. One runtime may attach to both, but profile movement or consolidation is a separate, opt-in migration—not a prerequisite for the unified extension.

Cross-source identity and exact-case matching

A normalized result should retain every provider's provenance while presenting one common shape:

type NormalizedCase = {
  canonicalKey: string;
  title: string;
  citations: string[];
  normalizedCitations: Array<{ volume: string; reporter: string; page: string }>;
  court?: string;
  dateFiled?: string;
  year?: string;
  docketNumber?: string;
  snippet?: string;
  snippetSource?: DiscoveryProviderId;
  discoveredBy?: Array<{
    method: "search" | "cited_by";
    provider: DiscoveryProviderId;
    seedCanonicalKey?: string;
    providerRank?: number;
  }>;
  sources: Array<{
    provider: ProviderId;
    providerId?: string;
    citedById?: string;
    url: string;
    sourceRank?: number;
  }>;

Deduplication rules

  1. Parse every reporter citation into a set of volume + canonical reporter + page tuples. Canonicalize punctuation, Unicode/ordinary spaces, and known reporter aliases such as U. S. and U.S..
  2. Merge when the two citation sets have any exact tuple in common, not only when providers display the same lead citation. This handles parallel citations such as U.S., S. Ct., and L. Ed.
  3. Normalized court + docket number + decision date.
  4. Normalized case name + court + year.
  5. Provider ID or canonical URL only as a within-provider fallback.

Before a merge, reject contradictory court, year, docket, or normalized title evidence. Ambiguous records remain separate and are marked for review; a weak title match never overrides conflicting structured metadata. The first assigned canonicalKey and folder assignment remain stable for the life of the session.

Cited-by seed resolution

  1. Normalize the supplied URL, provider ID, citation, docket, or query into portable identity evidence.
  2. Resolve that evidence independently in every selected citation-discovery provider. A CourtListener ID is never passed to Scholar, or vice versa.
  3. Expand the seed to every known parallel citation and provider opinion identity. Apply the same exact-match gate used by direct download and persist each resolved provider ID plus its evidence in the manifest.
  4. Enumerate every successfully resolved graph identity with its own cursor or partition queue. Merge duplicate citation edges without discarding which seed identity and provider produced each edge.
  5. Continue until every selected provider reaches a recorded terminal condition. A time slice produces a resumable paused job; a CAPTCHA, access failure, unsafe resolution, or unexhausted Scholar partition produces blocked/partial_failure, never a false complete report.

Meaning of complete: cited_by defaults to CourtListener and Scholar, runs both lanes concurrently, uses Scholar's record/blurb first for duplicates, and uses CourtListener as the principal exhaustive cursor stream. There is no result cap. “Complete” means every result exposed by each successfully enabled provider was traversed as of the recorded time. Google limits one Scholar query to 1,000 visible results, offers no bulk access, and does not warrant completeness; CourtListener also documents gaps that can affect its citation graph. The extension therefore reports provider_corpus_complete and always leaves universe_complete unclaimed.

Stage 1 report and Stage 2 promotion

Citation discovery and opinion retrieval are separate operations. The cited-by job saves only the normalized list and the provider-supplied result blurbs; it never performs a document lookup. When the user selects an entry for Stage 2, a separate direct_download call uses its already-resolved citation, docket, court, year, title, and provider URL. That call may then use FindLaw/Justia as bounded exact mirrors and may opt into case.md. This prevents exhaustive citation enumeration from multiplying into cases-by-document-providers downloads or thousands of model calls.

  • Record schema version, request fingerprint, query, mode, provider set, source URL/ID, retrieval time, match evidence, provider cursor, completeness marker, and content hash.
  • Use atomic writes for every checkpoint and collision-safe file names.
  • Resolve every relative destination from ctx.cwd; reject empty paths and keep this behavior identical across modes.
  • When omitted, save_path defaults to legal-research-downloads under ctx.cwd; the session name defaults to a sanitized mode plus UTC timestamp.
  • Track saved, skipped, failed, the pending download queue, each discovery provider's nextCursor, and exact document-lookup counts separately.
  • Write cited-by JSON incrementally from normalized result cards, then render the human-readable HTML report deterministically from that JSON. Its header records seed identity, as-of time, provider status, raw/unique/duplicate counts, full opinions downloaded (0), and LLM calls (0).
  • Each cited-by report entry contains only case name, citation set, court/date, provider-supplied blurb or the explicit missing-blurb marker, provider links/IDs, and citation-edge provenance. Raw opinion HTML is not part of this job.
  • Freeze each canonical key's folder assignment on first discovery. A slug plus stable key hash avoids order-dependent numbered folders.
  • On resume, validate the manifest version and request/source fingerprint, then load completed canonical keys and provider cursors so saved cases are neither downloaded nor counted twice.
  • For a cross-source case, permit multiple source HTML files while counting one normalized case.
  • Track download and summary status separately. A summary failure never deletes the HTML or changes a completed download to failed; it leaves a retryable summaryJobs entry.
  • Track discovered, downloaded, opinion-reviewed, citation-graph-reviewed, and external-citator-checked as separate states. Only legal_record_case_check may persist an external citator provider/time/treatment, and it does so per proposition rather than declaring an entire case universally valid.
  • Regenerate case.md only when it is missing, its recorded source hash differs, its selected model changed, or its prompt version changed. Resume does not pay for an identical completed summary twice; a stale running job is reset to pending after an interrupted process.

Resume invariant: for every provider, Scholar partition, and download queue, the manifest's next cursor identifies the first unit of work not known to be complete. Persist the current result page and its normalized entries before navigation, then atomically advance the cursor only after the report/checkpoint write succeeds. A time-slice exit is paused; only terminal-cursor evidence can produce exhausted.

Optional AI Markdown case briefs

Consent and authority: summarize=false is the default. Enabling it explicitly sends extracted opinion text to the selected configured model provider and may incur model charges. The saved provider HTML remains the source artifact; case.md is labeled AI-generated research assistance, not an official opinion, court syllabus, or legal advice.

Stage boundary: cited-by reports never enter this pipeline. They use provider-supplied result blurbs only and make zero model calls. Summarization becomes available only after an ordinary search result or selected cited-by entry is explicitly downloaded in Stage 2.

Post-download pipeline

Save and hash HTML→Checkpoint download→Extract source segments→Queue one summary job→Call Pi model→Validate evidence→Atomically write case.md
  1. The raw opinion and normalized metadata are saved successfully before any model call. Search-tab restoration and the provider cursor are not held open by summarization.
  2. A single-worker enrichment queue may run alongside later browser navigation, but the parent tool awaits or checkpoints every queued job before returning.
  3. Each job receives only one case's metadata and numbered opinion segments. It has no research tools and no conversation history, preventing recursive tool calls and cross-case contamination.
  4. Success, failure, model usage, and retry state are recorded independently. Cancellation leaves the first unfinished summary job pending for manifest resume.

Grounding and validation

Ask the model for a versioned JSON case-brief object containing overview, facts, procedural posture, issues, holdings, reasoning, rule, disposition, separate opinions, uncertainties, key passages, and supporting segment IDs. The prompt treats opinion text as quoted untrusted data and explicitly forbids following instructions found inside it. Validate the JSON shape, all segment IDs, exact quotations, case identity, and maximum field lengths. Allow at most one repair call for invalid structure; otherwise preserve the download and mark the summary failed.

Long opinions and cost bounds

  • If the complete opinion fits within 65% of the selected model's context window, use one case-brief call.
  • Otherwise summarize ordered, non-overlapping segment groups and perform one final synthesis from the grounded intermediate records. Original segment IDs survive both stages.
  • Default to six nested calls per case and enforce an absolute maximum of twelve, including a possible repair call. A case that cannot fit within that budget is marked summary_failed; its download remains complete.
  • When summarization is enabled, bulk workflows permit at most 100 downloaded cases. Preflight reports selected provider/model, cases requested, typical one-call cost shape, and the worst-case nested-call count.
  • The final workflow result reports downloaded, summarized, summary_failed, and summary_pending separately, together with aggregate input/output tokens and model usage returned to Pi.

Implementation sequence

Phase 0

Pass access and contract gates

Review each provider's current terms, robots directives, API/bulk-data permissions, access restrictions, and acceptable request rates before collecting fixtures or implementing automation; record allowed paths and stop conditions. Use a flat enum-driven Pi schema with mode-specific preflight validation so the contract does not depend on anyOf rendering. Freeze the two-stage boundary, exhaustive cited-by completion vocabulary, time-slice/resume rules, source strategy, and profile-retention policy.

Phase 1

Freeze behavior with allowed fixtures

Where the access gate permits it, capture representative search, no-result, opinion, verification, pagination, filter, cited-by first/middle/terminal pages, missing-blurb cards, and Scholar partition-boundary behavior for the current CourtListener and Scholar extensions. Add characterization tests before moving code. Store fixtures as test data only and document their capture date.

Phase 2

Extract the shared runtime

Move CDP/API transport, Chrome lifecycle, abort handling, queues, tab leases, timing, atomic writes, progress events, and archive helpers behind internal interfaces. Add independent Scholar/CourtListener lanes, deterministic page-wave barriers, cited-by cursor/partition queues, and time-slice checkpoints while preserving each provider's pacing and access rules. Normalize path semantics and public result types. Add the isolated Pi model-call wrapper, single-worker summary queue, source-segment builder, validated Markdown renderer, and nested-usage accumulator.

Phase 3

Port CourtListener and Scholar without regression

Implement both adapters, all four workflows, metadata-only cited-by entries, deterministic HTML/JSON cited-by reports, legal_read_case chunk continuation, legal_record_case_check, browser handoff, per-provider manifest cursors, optional post-download case.md generation, and the decided one-release compatibility wrappers. Reuse the existing profile directories; do not require profile migration.

Phase 4

Add FindLaw as a document adapter

Implement direct-URL validation, tightly bounded exact-case lookup, confidence scoring, opinion extraction and stable source segments from #caselaw-content, and exact/no-match/ambiguous fixtures. Do not expose Cludo pagination as general search.

Phase 5

Add Justia as a document adapter

Implement direct-URL validation, bounded exact-case resolution restricted to supported opinion URL families, and stable source-segment extraction from both general and Supreme Court opinion layouts. Do not expose Custom Search pagination as general discovery.

Phase 6

Complete exhaustive cross-source cited-by reporting

Resolve every seed identity independently in CourtListener/Scholar, estimate workloads, enumerate every permitted cursor/partition without a result cap, checkpoint before navigation, merge on overlapping normalized citation sets, and prove that no opinion adapter or model call runs. A selected report entry moves to Stage 2 through a separate direct download; only that later operation may use FindLaw/Justia as exact alternative opinions.

Phase 7

Package, migrate, and observe

Bundle one extension entry point, publish the compatibility/removal schedule, document the two stages, provider-corpus completeness language, time-slice resume, external-citator recording, and summary consent/cost/model behavior. Add structured diagnostics and migration notes, repeat the access review, and run conservative opt-in live smoke tests.

Test plan and acceptance criteria

Automated tests

  • The selected Pi schema shape renders clear mode-specific fields and rejects mixed modes, multiple selector kinds, provider IDs without providers, and auto combined with explicit providers.
  • The schema rejects FindLaw/Justia inside every DiscoverySelection, but accepts them in DocumentSelection and direct provider selectors.
  • The schema rejects summarize on search, summary_model without summarize=true, and every download, document-source, mirror, opinion, and model field on cited_by.
  • With summarize=false or omitted, no nested model call occurs and no case.md is created.
  • Summary preflight selects the active or requested session-allowed model, verifies configured authentication, and fails before browser navigation when the model cannot be used.
  • Discovery auto uses Scholar then CourtListener; ordered fallback and concurrent deterministic combine never call FindLaw/Justia and preserve discovery rank.
  • Deferred-provider tests prove that combined mode launches Scholar and CourtListener before either finishes, waits for the page barrier, and returns the same Scholar-first merge regardless of response order.
  • A timeout, CAPTCHA, or layout failure in one combined lane is recorded as partial coverage without discarding the other lane's results or cursor; cancellation aborts both.
  • Document discovery, fallback, and all_available routing perform only exact identity lookups, enforce the confidence gate, and charge alternative providers to the mirror budget.
  • Unsupported filters fail during preflight, native filters are transmitted, and post-filters report inspected and dropped counts without opening opinions in search.
  • Every CourtListener/Scholar discovery fixture parses exactly the rendered result-card count or fails closed with a layout-change error.
  • FindLaw/Justia adapters expose no general-search or cited-by method; their exact-lookup fixtures cover direct URL, unique citation match, no match, ambiguity, and lookup-page exhaustion.
  • No-results, blocked, CAPTCHA/verification, alert, and unexpected-page fixtures are distinguished.
  • Each Next action proves both page identity and content changed; repeated/cyclic pages stop safely.
  • search never calls an opinion-opening adapter method.
  • search_download restores the same result page before continuing and stops at case, page, and runtime budgets.
  • cited_by resolves all known parallel seed identities and separate provider IDs, reports estimates/access ceilings, maintains independent cursors and Scholar partition queues, merges any overlapping normalized parallel citation, and has no result/page cap.
  • First, middle, and terminal cited-by fixtures prove that every result card becomes exactly one normalized list entry or a documented duplicate, the next cursor advances only after checkpoint, and only terminal evidence produces exhausted.
  • A cited-by time-slice exit returns paused, preserves the first uncompleted cursor/partition, and resumes without gaps or duplicate report entries. A CAPTCHA, blocked partition, layout failure, or unsafe seed resolution can never be reported as complete.
  • The cited-by adapter never calls openOpinion, any document resolver, or ctx.modelRegistry.complete; its report shows full opinions downloaded and LLM calls as zero.
  • The cited-by HTML and JSON contain case name, citation set, court/date, provider blurb or missing marker, source links/IDs, and edge provenance. Scholar's blurb wins for duplicates when present while every provider's raw blurb remains in JSON provenance.
  • Cross-provider retrieval never exceeds max_mirror_lookups; its default of zero cannot cause hidden searches.
  • direct_download saves one unique match and refuses tied/low-confidence candidates.
  • legal_read_case returns stable 12,000-character chunks with an exact next offset and reaches an unambiguous end-of-document state.
  • legal_record_case_check records a review per proposition, verifies submitted quotations against the downloaded opinion when available, leaves omitted citator work visibly unchecked, and never converts free cited-by completion into a “good law” status.
  • Cancellation at every await point produces a valid manifest whose independent cursors and pending queue resume at the first incomplete unit.
  • Folder assignments stay stable when discovery order changes, and completed canonical keys are not re-counted on resume.
  • Relative paths resolve from a mocked ctx.cwd for all providers and all modes.
  • The saved HTML hash matches the exact unmodified bytes; metadata appears only in the JSON sidecar.
  • A successful summary produces one deterministic case.md whose source hash, model, prompt version, and generated time match the manifest.
  • Every summary segment link exists in that case's extracted opinion; every quoted passage is exact; malformed or hallucinated references fail validation.
  • Opinion text containing prompt injection cannot alter the requested JSON contract, select tools, change files, or leak into another case's isolated model context.
  • Long-opinion map/reduce preserves original segment IDs and obeys the per-case model-call ceiling, including its single repair attempt.
  • Model timeout, refusal, invalid JSON, context overflow, cancellation, and exhausted call budget preserve the completed HTML and record a retryable summary outcome.
  • Resume skips summaries whose source hash and prompt version still match, retries pending/failed jobs, and regenerates stale Markdown atomically.
  • Nested model usage is aggregated across chunk, synthesis, and repair calls and returned on the Pi tool result.
  • Each legacy wrapper translates parameters correctly and emits the documented deprecation notice.
  • Source HTML containing prompt-like or hostile text remains untrusted data and cannot change tool control flow.

Release acceptance

  • Pi loads one bundled extension without diagnostics and presents the two-stage workflow, four-mode research schema, reading, case-check recording, and browser tools clearly.
  • All four workflows use Scholar/CourtListener for discovery; auto prefers Scholar and falls back to CourtListener when Scholar is unavailable or cannot honor a requested capability.
  • Combined discovery runs Scholar and CourtListener concurrently, merges at page barriers with Scholar first, and remains deterministic when their response order changes.
  • FindLaw and Justia work for validated direct URLs, reading, exact opinion lookup, and document download, but never appear as general-search or cited-by providers.
  • No requested filter is silently ignored. Search/download operations retain explicit case/page/runtime ceilings; cited-by alone uses no result cap and instead runs as a checkpointed, resumable, time-sliced job until every enabled provider exhausts or records a blocking failure.
  • Every completed download is traceable to a source URL and manifest record.
  • A stopped multi-provider run resumes each provider and its download queue without overwriting or recounting completed cases.
  • A cited-by run can enumerate beyond 1,000 merged candidates without opening or downloading an opinion, and a stop/resume cycle produces the same normalized report as an uninterrupted fixture run.
  • Chunked opinion reading remains available for CourtListener and Scholar and is implemented for FindLaw and Justia.
  • Enabling summaries creates one evidence-linked case.md per successfully summarized canonical case, while disabling summaries makes zero nested calls.
  • A summary failure never corrupts, deletes, or downgrades a completed source download, and the manifest can resume the enrichment independently.
  • Pi reports the selected summary model and all nested usage in the workflow result and session accounting.
  • User-facing cited-by output reports the seed, selected providers, as-of time, provider status, partitions/cursors, raw/unique/duplicate counts, and completion basis. It says “retrieval complete for the selected provider corpus” only after every selected graph is exhausted, always says universe_complete: not_claimed, and states exactly why paused, blocked, cancelled, or failed runs are not complete.
